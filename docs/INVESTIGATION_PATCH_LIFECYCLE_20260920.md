## Defect 1: a no-change operation destroys the migration chain

Let S0 be original tablet bytes, S1 performance-only, S2 performance plus FANS.
The first two successful installs record:

```
performance: original S0 -> installed S1
FANS:        original S1 -> installed S2
current file: S2
```

Updating performance again correctly preserves both patches and changes no
aircraft bytes. However `ContentPatchEngine.Execute` calls `RecordState` even
on the no-change path. `BuildFileState` retains the old original/backup and
replaces the installed hash with the current combined file hash:

```
performance: original S0 -> installed S2
FANS:        original S1 -> installed S2
current file: S2
```

Both backups still exist and match their recorded hashes. `CatalogGroupMigration`
requires every remaining record to be consumed by one backwards linear hash
walk. That walk cannot consume this branched history, whichever edge is selected
first. This reproduces the exact tablet error without backup loss, manual edits,
or a failing patch payload. Delta installation is not required for this defect;
the restore probe confirms it remains after reverting the delta.

Measured tablet hashes:

- S0: `7c9e445a2a002f1ef81a0b738ad3c3b791a63c2c313d44d993517e260cd32141`
- S1: `efcdf3fb58100d59f44e1bd9ac8c1084240cc016f1b031609047d568a5cf63ec`
- S2: `93e53cc017755243c5bc2aac021a26eea684c967d4de98b36331e1d7be68a478`

## Defect 2: official delta changes invalidate standalone ownership

The S1.51C delta does not contain or delete the tablet/FMS script. It does replace
the cockpit object. Its new bytes match neither the standalone FANS original nor
its installed hash. The delta's `RecordAircraftUpdateState` updates aircraft
version/backup metadata but leaves patch ownership unchanged.

Migration then rejects the official changed object before the normal structural
patch planner can assess it. Restoring the delta through the production operation
restores the preceding object and makes the unrefreshed history migratable again.

Object hashes:

- Original S1.50: `d702eb4898871cbb079045915ede7579d3cc6b64710c66b828dbf354c515e5f7`
- Standalone FANS installed: `a112666959edeb92a0611295010d4fe8d63bbf1725f524480503e7a6cb865b29`
- Official S1.51C object: `a0b8681870c099fe4b770e22ecd659434cbcb3af71479e3f9d459d8810012d3d`

Full-baseline replacement already snapshots and resets content ownership, and
full restore swaps ownership with the files. Incremental apply/restore only
records aircraft-level metadata; it does not provide equivalent per-file
reconciliation for content patch ownership. A blanket state reset on delta apply
would also be wrong: unchanged patched files must retain valid ownership.

## Recovery gap: original bytes present, backup deleted

0.13.12 accepts a reset-to-original file only if the historical original backup
also exists and verifies. The clean-original-with-deleted-backups scenario
therefore still blocks even after delta restore. The state file is independent
of the backup directory, so deleting only backups cannot reset ownership.

This is distinct from defect 1. Explaining all failures as missing backups would
be incorrect. Completely absent original bytes also cannot be claimed recovered
without an independent verified source.

## Why preceding validation missed these cases

- Earlier full-replacement tests validated replacement generations, not this
  standalone -> no-change refresh -> group transition.
- The existing shared-target test checks that repeating a standalone package
  preserves both patches, but does not subsequently migrate that history.
- Previous chain tests construct linear/no-change hash records directly. They
  do not create the branched record through `ContentPatchEngine`.
- A clean install has no old standalone ownership to migrate.
- The deleted/corrupt-backup test expressly expects rejection. It does not test
  recovery when the current target already supplies verified original bytes.

## Correction contract before another release

1. Separate observation of current composite bytes from immutable patch
   transition/original evidence. Prevent successful repeated operations from
   making valid history unmigratable.
2. Recover histories already produced by released versions using verifiable
   package/file evidence; changing only future state writes is insufficient.
   Do not choose the oldest backup or discard unmatched records by guesswork.
3. Record authoritative per-file baseline changes from a verified aircraft delta
   together with ownership changes, and restore both in the same generation.
   Preserve ownership for files the delta did not change.
4. When current bytes verifiably equal the recorded original, support creation
   of a fresh verified backup in the transaction. Do not fabricate historical
   restore availability for other missing originals.
5. Log the failure category, actual/expected hashes, source package identities
   and backup verification outcome. The current shared message hides materially
   different causes.
6. Re-run these actual operation sequences after correction, extending them to
   group apply/repeat/optional selection/restore, interrupted writes and rollback,
   and unknown modifications that must remain protected.

## Implemented correction and acceptance evidence

- No-change observations no longer overwrite a standalone component's last
  actual write hash. This is decided per file, including mixed transactions.
- Migration validates the reachable hash graph, including verified immutable
  transaction edges anchored to each active component's original backup. A
  disconnected/ambiguous history or an unavailable required original still
  blocks. Snapshot-only overlapping histories are not guessed into a chain.
- Exact current original bytes can replace a missing/corrupt backup. The new
  backup is captured in the write transaction with rollback, not in planning.
  An absent patch-created file also matches its recorded absent original.
- Aircraft deltas snapshot patch ownership, clear ownership only for the files
  they replace/delete, and retain ownership/selection for other files. Delta
  restore validates all backups before writing, restores affected ownership,
  and rolls back file writes on failure. A group can incorporate the restored
  standalone ownership for those targets without overlapping existing owners.
- Legacy delta recovery is narrowly constrained: one old owner, a verified
  aircraft-update preimage matching its recorded installed hash, a verified
  old original, and selected structural handlers. The normal patch pipeline
  must validate current bytes. Whole-file copy targets never use this route.
  Current bytes become the new backed-up baseline, preserving the official
  delta object on subsequent group restore.
- Successful content transactions make installation ownership authoritative;
  historical per-variant entries cannot resurrect removed source components.
- Rejections now identify the current hash, source packages and whether backup
  verification or disconnected/ambiguous history caused the block.
